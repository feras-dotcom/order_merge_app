# Shopify app development

This app is scaffolded from a Shopify app template. See the README for framework-specific details.

Use the [Shopify AI Toolkit](https://shopify.dev/docs/apps/build/ai-toolkit) for all Shopify API and platform work. If missing, install it in the agent host per that page (or `npx skills add Shopify/shopify-ai-toolkit --list` for skill-compatible hosts) — do not add tooling to this repo.

## Verification

- `npm test` — Vitest unit/integration tests (merge engine runs against an in-memory fake Shopify in `tests/fake-shopify.ts`).
- `npx tsc --noEmit` — one pre-existing error in `app/shopify.server.ts` (duplicate `@shopify/shopify-api` session types) is known and unrelated.
- `npx eslint app tests scripts --ext .ts,.tsx`
- `npm run build`
- Real-Postgres store tests (claims, work items, operation leases, legacy apply and cutover paths; they run with the database session timezone set to Asia/Tokyo to prove the UTC clock discipline): `MERGESHIP_TEST_DATABASE_URL=postgresql://... npx vitest run tests/postgres-stores.test.ts`. The URL must point at a disposable database; the test runs `prisma migrate deploy` against it.
- Legacy reconciliation plan/drive tests run in `npm test` (`tests/legacy-reconcile.test.ts`, canned fake admin + memory stores); evidence-ladder pagination and fail-closed cases live in `tests/evidence.test.ts`.
- Two-process contention test (two real workers, real Postgres, an in-test fake-Shopify HTTP server; covers contention, delayed/lost commit responses, crash takeover, post-completion re-merge and REVIEW_REQUIRED parking — the child env knobs are `LEASE_TTL_MS`, `CRASH_AT`, `SWEEP_ONLY`, `SWEEP_MAX_MS`): `MERGESHIP_TEST_DATABASE_URL=postgresql://... npx vitest run tests/two-process.test.ts`. Run the two database-backed files one at a time: they truncate the same disposable database, so running them in one vitest invocation makes them interfere.
- Live protocol verification against a dev store (creates and cancels real test orders; token/agreement/staff-note evidence and the end-to-end merge path): `MERGESHIP_LIVE_STORE=<store>.myshopify.com npx vitest run tests/live-protocol.test.ts` (override fixtures with `MERGESHIP_LIVE_VARIANT`, `MERGESHIP_LIVE_VARIANT2`, `MERGESHIP_LIVE_CUSTOMER`).
- Operator scripts (legacy reconciliation, work requeue, backfill, kill switches, worker heartbeats) run with `npx vite-node scripts/<name>.ts`; they read `DATABASE_URL` and the Shopify environment from the operator's shell and print a clear error when `DATABASE_URL` is unset. The full kill-switch and cutover procedure is `docs/RUNBOOK.md`.
- Validate any new GraphQL against the pinned API version 2026-04 with `npx shopify app execute --store <store> --version 2026-04 --query-file <file>`. The app pins `ApiVersion.April26` in `app/shopify.server.ts`.

## Merge engine invariants

- Never replace, only reconcile. Once an order-affecting Shopify request may have been dispatched, no conflicting operation may touch those orders until the original is conclusively reconciled or parked in `REVIEW_REQUIRED`.
- Every merge-path Shopify call goes through `gql()` in `app/lib/graphql.server.ts` (fails on transport/top-level errors, missing payload, userErrors).
- Safety is durable, not in-memory: a `MergeOrderLock` row (one per order, unique) is held for the life of every v2 `MergeOperation`, and orders involved in a v1 PENDING_COMMIT / COMMITTED / NEEDS_REVIEW op are never merged again. Claims (`MergeClaim`, all-or-nothing, `app/lib/claims.server.ts`) only provide liveness — leases and their fences stop a stale worker from writing, but the durable lock is what keeps orders out of other merges. All v1 blocking/unfinished journal queries filter `protocolVersion = 1`: the legacy `status` column on a v2 row is only a shield for old readers (NEEDS_REVIEW while non-terminal, the terminal phase otherwise) and never a resume signal; the dispatch gate never writes it. A READY→ABANDONED transition additionally requires that no `EDIT_COMMIT` attempt row exists — an op that may have dispatched can never be abandoned.
- A `MergeMutationAttempt` row is written **before** every order-affecting Shopify request (write-ahead), via `openDispatchGate`. The gate checks the kill switches (`AppControl.newMergesEnabled` / `completionEnabled` / `MERGESHIP_MUTATIONS` env, plus `allowShops`) atomically with the attempt insert: it locks the op row FOR UPDATE, then reads `AppControl` FOR SHARE, while `setControl` takes FOR UPDATE — so a disable committed while a gate waits on the op lock is always observed, and a request can only leave the process if its gate committed before the disable did (the documented boundary). `createOperation` enforces `newMergesEnabled` the same way inside its transaction, and `executeMerge` returns `MERGES_DISABLED` before its first Shopify read. The attempt is recorded SUCCEEDED / REJECTED / UNKNOWN from the response. Every `orderEditCommit`/`orderCancel` userError is UNKNOWN — a Shopify answer does not prove the change was never applied, so evidence (or a human in REVIEW_REQUIRED) decides; REJECTED is reserved for the provable fence-before-send case (a fence failure before `admin.graphql` is invoked records `not dispatched: ownership lost before send`) and for the idempotent cosmetic kinds.
- Commit evidence is a `MergeCalculatedOrder` freeze plus, after commit, tokened line items: each transferred line carries a ManualDiscountApplication description `Merged from #S, already paid · MS-<opToken>-<idx>` and must appear as a `ProductSale` in one `OrderEditAgreement` attributed to this app (`currentAppInstallation.app.id`) with `happenedAt` inside the dispatch window. `appliedEvidence` stores `{ agreementId, happenedAt, lines[] }`. The scan paginates line items and agreements in independent documents with fail-closed `pageInfo` validation (`nextPageCursor`/`IncompletePageError` — a finished connection never restarts), and an `APPLIED` verdict requires the one-request `MergeTransferRecheck` (fresh primary `Order` state plus `nodes(ids:) { ... on LineItem }` for every token line) to reproduce the scanned values; a line or the primary mutated mid-scan is an ANOMALY, never a cancel.
- `cancelPrecondition` revalidates from live reads immediately before each `orderCancel`: the secondary's order state and its lines against the frozen manifest (`sourceManifestMismatch`; native v2 entries bind `sourceLineItemId` + `sourceQuantity`, legacy-converted entries use the multiset), the freshly re-verified evidence, the rechecked token lines' `unfulfilledQuantity`, the primary's own `orderStateIneligibility`, and the shared `groupOrderIncompatibility` order rules + recorded customer — every failure parks REVIEW_REQUIRED with locks retained.
- `orderCancel` is asynchronous and runs only after applied evidence exists for that secondary and the secondary is still untouched; it is proven by reading back `cancelledAt` plus a staff note containing `MS-<opToken>`. Ops converted from the v1 journal (`calculatedOrderId IS NULL`) additionally accept the v1 note `merged into #P by MergeShip` — v2-created ops never do.
- `RECOMMIT_SAME_CALC` stays false: a calculated order is committed at most once; a second `orderEditCommit` for the same calculation is never issued — doubt is resolved by re-reading evidence, not by re-sending.
- Every ownership-sensitive write is lock-then-validate inside `withOwnershipTx` (`lock_timeout` 2s, `statement_timeout` 5s): `SELECT … FOR UPDATE` on the row(s) first, then the token+lease-conditional UPDATE on the database UTC wall clock (`clock_timestamp() AT TIME ZONE 'UTC'`, never a JS Date or bare `now()`). The wait must happen before the predicates are evaluated — PostgreSQL does not re-evaluate a conditional UPDATE whose row was locked but not changed, so a bare conditional UPDATE can write past lease expiry. All timestamp columns store the naive UTC wall clock: a `Date`/`timestamptz` bound from JS must go through `(?::timestamptz AT TIME ZONE 'UTC')` — a bare bind is read in the session timezone and lands hours off on non-UTC sessions. The evidence/retry ladders are absolute from `firstDispatchAt`/`dispatchedAt`. A worker that loses its lease (`OwnershipLostError`) stops without writing.
- `orders/create` records a PENDING `ProcessedWebhook` work item before answering 200; the sweeper (`app/lib/background-worker.server.ts`, from `entry.server.tsx`, disabled with `DISABLE_BACKGROUND_WORKER=true`) reaps claims, drives due operations, exhausts retryable items and claims new work. Outcomes are classified terminal vs contention/transient (`app/lib/order-work-processor.server.ts`); never mark work DONE on a transient failure. Siblings parked under a `REVIEW_REQUIRED` op (or a v1 NEEDS_REVIEW op) are excluded from matching; non-review locks and live claims keep them "busy".
- Legacy reconciliation (`app/lib/legacy-reconcile.server.ts`, CLI `scripts/legacy-reconcile.ts`, dry-run default) converts blocking v1 ops to v2: an overlap pre-pass parks two ops sharing an involved order before any live read; evidence matches are exact (`Merged from #N` description and `merged into #P by MergeShip` staff note — `#123` must never prove `#12`, a different primary never proves ours). A converted op can never dispatch a fresh `orderCancel`: an open secondary without `cancelRequestedAt` is `CANCEL_REVIEW` (never `CANCEL_READY` — v1 kept no write-ahead cancel record, so dispatch is unprovable), `cancelRequestedAt` + open is `CANCEL_IN_DOUBT` with a synthetic UNKNOWN `ORDER_CANCEL` attempt at the recorded timestamp, and only a verified cancellation or an in-doubt one lets the op reach `APPLIED`. `applyLegacyVerdict` is one transaction per op — it `FOR UPDATE`-locks the operation row and re-reads it first, and writes nothing unless `protocolVersion` is still 1 and the snapshot it applied against (status, `updatedAt`, involved orders) is unchanged ("skipped" otherwise) — then locks, conversion, MergeRecords, synthetic attempts, all-or-nothing.
- Cutover work policy (`app/lib/cutover.server.ts`; procedure in `docs/RUNBOOK.md`): `scripts/requeue-cutover-work.ts --cutover-at <iso> [--since <iso>] [--older-legacy requeue|review|exclude] [--apply]` reconsiders `DONE` `ProcessedWebhook` rows created since `cutoverAt − MAX(Settings.mergeWindowHours)` (24h fallback; an explicit `--since` newer than that is refused) with NULL/LEGACY outcome, excluding orders a live `MergeOrderLock` holds or a `MergeRecord` already merged (both lists are printed). Rows older than the window are provably stranded and need `--older-legacy`: `requeue` (back to PENDING), `review` (`status='REVIEW'` with an operator reason — surfaces in the dashboard review count), or `exclude` (stamped `CUTOVER_EXCLUDED_BY_OPERATOR`, left DONE/LEGACY); dispositions obey the same exclusions and are idempotent. Apply also extends only PENDING rows whose deadline is inside an hour. `scripts/backfill-recent-orders.ts --since <iso> [--apply]` upserts one item per order — inserts absent rows, reopens only `DONE`/NULL/LEGACY rows, and never touches locked/merged orders, v2 outcomes, or `REVIEW` rows; its Shopify read (`listBackfillOrderIds`) throws on any error or incomplete page, never silently treating a bad read as empty. Every `--apply` path first calls `requireControlsOff` — with either mutation switch on it exits 2 before any write. Re-running either tool is a no-op. `scripts/app-control.ts` refuses to clear the allowlist while a switch is on (an empty allowlist means ALL shops) unless `--allow-all-shops` is passed.
- Automatic merging is opt-in (`Settings.autoMergeEnabled` defaults to false).
- Location rule (`resolveMergeLocation`): with the optional `read_merchant_managed_fulfillment_orders` scope (merchant grants it from Settings), every open fulfillment order of every order must be OPEN/UNSUBMITTED/unheld, share one assigned location, and account for every unfulfilled unit; without the scope, only single-active-location shops qualify. The `FulfillmentOrder.location` field does not exist — use `assignedLocation { location { id } }`.
